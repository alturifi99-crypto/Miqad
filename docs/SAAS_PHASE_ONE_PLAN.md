# خطة المرحلة الأولى: تحويل مقعد إلى منصة متعددة الشركات

الحالة: نُفذ أساس تطوير محلي مستقل في `server/` بعد الفحص والخطة. اجتازت اختبارات PostgreSQL وAPI للعزل. هذه ليست نسخة SaaS إنتاجية، ورُبطت واجهة الموقع الحالية بالخادم في بيئة التطوير دون نقل بيانات المستخدم الحقيقية. راجع `server/README.md` للتشغيل وحدود التنفيذ.

## 1. نتيجة فحص المستودع

- النسخة المفحوصة: `e72312b`، وملفات التشغيل `index.html` و`styles.css` و`app.js`.
- لا يوجد خادم API، ولا قاعدة بيانات أو migrations أو مصادقة أو جلسات أو package manifest لتطبيق خادمي.
- لا يستدعي التطبيق حاليًا API لحفظ الضيوف والحجوزات. `load()` و`persist()` تقرآن وتكتبان في المتصفح.
- `miqadStateV2`: الصفوف وعدد الكراسي والضيوف ومواقعهم والوفود ورئيس كل وفد. الحجز هو `rowId` و`seat` داخل سجل الضيف، وليس كيانًا مستقلًا.
- `miqadGuests`: مصدر البيانات القديم الذي يحتفظ به التطبيق عند النقل المحلي.
- `miqadWorkspacePrefs`: أسماء محلية للفعالية والقاعة والمستخدم؛ ليست هوية مستخدم أو ملكية شركة.
- مفاتيح تفضيلات الواجهة منفصلة، ولا تحتاج إلى أن تصبح بيانات مشتركة بين الشركات.
- توجد اختبارات متصفح للمقاعد والسحب والتبديل والوفود والواجهة والقائمة، ولا توجد اختبارات عزل خادمي أو SQL لأنهما غير موجودين.
- لم يظهر اتصال قاعدة بيانات أو إعداد مصادقة أو بريد ضمن أسماء المتغيرات التي فُحصت. هذا يخص هذه البيئة، ولا يثبت عدم امتلاك المستخدم خدمات خارجها.
- ملفات Git لا تتضمن بيانات مستخدمي الموقع المخزنة على أجهزتهم. لا يمكن استخراجها من المستودع أو استنتاج الشركة المالكة من اسم الفعالية.

لم تُعدّل ملفات التطبيق أو تخزينه أثناء هذا الفحص، ولم تُنشأ بيانات شركات أو حجوزات بديلة.

## 2. البنية المقترحة

الخيار الافتراضي المقترح عند عدم وجود بنية قائمة:

- واجهة عربية RTL تحتفظ بمكونات مقعد الحالية ووظائفه.
- خادم Node.js LTS مع TypeScript وAPI منظم، ومكتبة مصادقة مدعومة بدل كتابة التشفير وإدارة كلمات المرور يدويًا.
- PostgreSQL مع migrations صريحة، وقيود علاقات وRLS على كل جدول تابع لشركة.
- نشر الواجهة وAPI تحت الأصل نفسه خلف HTTPS لتبسيط حماية الجلسات وCSRF؛ يمكن إبقاء الواجهة على استضافة ثابتة إذا ضُبط أصل API وCORS والجلسات بدقة.
- GitHub Pages لا يشغّل خادم Node.js أو PostgreSQL. لا يُحوّل الموقع الحالي إلى وضع SaaS قبل توفر استضافة مناسبة واختبار بيئة تجريبية.
- جلسات خادمية بملفات تعريف ارتباط HttpOnly وSecure وSameSite، مع انتهاء وإبطال وتدوير الجلسة بعد الدخول أو تغيير الصلاحيات. لا تُخزن رموز الدخول في localStorage.
- مزود بريد لتأكيد العناوين ودعوات الموظفين واستعادة كلمة المرور. تحفظ الأسرار في إعدادات الخادم الآمنة، ولا تُطلب قيمها في المحادثة أو تُضمَّن في المستودع.

يمكن استخدام خدمات مصادقة وقاعدة بيانات مدارة إن كانت متوفرة، مع بقاء قيود العزل واختباراته إلزامية.

## 3. نموذج البيانات

| الكيان | الملكية والارتباط |
| --- | --- |
| users / sessions | هوية المستخدم وجلساته؛ ليست قائمة ضيوف الفعاليات |
| tenants | الشركة، حالتها، والبيانات الإدارية |
| memberships | المستخدم + الشركة + الدور + حالة العضوية |
| invitations | دعوة محددة للشركة والبريد والدور، بمدة صلاحية واستخدام واحد |
| events | فعالية تابعة لشركة واحدة |
| halls | قاعة تابعة لشركة واحدة ويمكن استخدامها في فعاليات متعددة |
| event_halls | استخدام القاعة في فعالية محددة، ومخطط مستقل لذلك الاستخدام |
| seating_rows / seats | الصفوف والكراسي داخل event_hall، مع رقم كرسي يبدأ من 1 لكل صف |
| guests | ضيف في فعالية محددة، مع حقوله الحالية والمرافقين والملاحظات |
| reservations | تخصيص ضيف لمقعد في فعالية/قاعة محددة |
| reservation_history | سجل انتقال وتبديل وإخلاء المقاعد دون ضياع التاريخ |
| delegations / delegation_members | وفد ورئيس وأعضاء في فعالية الشركة نفسها |
| audit_logs | العمليات الحساسة ومن قام بها وفي أي شركة |
| import_batches / import_mappings | مصدر الاستيراد وبصمته ونتيجته وربط المعرّفات القديمة |
| plans / tenant_subscriptions / entitlements | تعريف الباقات والحدود والاستحقاقات، دون ربط دفع |
| platform_admins | إدارة مالك المنصة، منفصلة عن ملكية الشركات |

كل جدول تشغيلي يحتوي `tenant_id NOT NULL` ومعرّفات الفعالية والقاعة المناسبة. لا يكفي tenant_id دون قيود علاقات مركبة.

أمثلة القيود المطلوبة:

- لا يشير ضيف أو وفد أو مقعد إلى فعالية أو قاعة في شركة أخرى: مفاتيح أجنبية مركبة تشمل tenant_id وevent_id عند الحاجة.
- لا يكون رئيس الوفد خارج أعضائه أو خارج فعاليتهم؛ ولا ينتمي الضيف إلى وفدين في الفعالية نفسها.
- لا يوجد حجزان نشطان للمقعد نفسه، ولا مقعدان نشطان للضيف نفسه داخل الفعالية.
- لا يُعاد استخدام معرّف صف محذوف أو تغيير هوية مقعد لمجرد تغيير اسم الصف.
- المخطط منفصل لكل استخدام قاعة في فعالية؛ لا تؤثر حجوزات فعالية على فعالية أخرى في القاعة نفسها.

لتنفيذ التبديل دون تعارض لحظي: معاملات تقفل المقاعد/الحجوزات بترتيب ثابت، وقيود UNIQUE قابلة للتأجيل داخل معاملة التبديل، مع سجل تاريخ مستقل. واجهة المستخدم لا تحسم السباق؛ قاعدة البيانات هي الحكم الأخير.

## 4. العزل والصلاحيات

### الخادم

1. يتحقق من جلسة المستخدم ومن عضويته النشطة في الشركة المطلوبة قبل كل عملية.
2. يمكن استقبال معرف شركة للتنقل بين عضويات المستخدم، لكن لا يُوثق به دون التحقق الخادمي؛ لا يحدد جسم الطلب مالك السجل.
3. يضبط سياق المستخدم والشركة محليًا داخل معاملة PostgreSQL واحدة. لا يستعمل إعداد اتصال دائم يمكن أن يتسرب مع connection pooling.
4. يتحقق من صلاحية العملية نفسها، لا من إمكانية إظهار الزر فقط.
5. يطبّق التحقق أيضًا على البحث والإحصائيات والتصدير والاستيراد والوفود والحجوزات وأي مهام خلفية.
6. لا يرد ببيانات المورد إن كان المستخدم غير مصرح له؛ تُستخدم 404 للمورد غير المتاح و403 للعمليات المحظورة وفق سياسة ثابتة لا تكشف بيانات شركة أخرى.

### قاعدة البيانات

- `ENABLE ROW LEVEL SECURITY` و`FORCE ROW LEVEL SECURITY` للجداول التابعة للشركات.
- سياسات USING وWITH CHECK لكل عملية، تشمل الشركة والعضوية والأدوار المناسبة؛ السياسة الافتراضية ترفض عند غياب السياق.
- حساب تشغيل API ليس superuser ولا مالك الجداول ولا يمتلك BYPASSRLS. حساب migrations منفصل ولا يُستخدم لتشغيل التطبيق.
- تحدد منح SQL والسياسات ما يمكن قراءته أو تغييره. سياسات الجداول الأبناء لا تعتمد على إخفاء صف الأب في الواجهة.
- تُختبر السياسات باستخدام حساب تشغيل التطبيق الحقيقي، وليس فقط حساب migration يتجاوزها.
- بيانات الهوية والجلسات العامة لها صلاحيات خدمة مصادقة منفصلة؛ لا يُعطى مستخدم API وصولًا عامًا إلى حسابات المستخدمين.
- لا تصل بيانات اتصال PostgreSQL أو مفاتيح خدمة ذات امتيازات إلى المتصفح.

### الأدوار الأولية

| الدور | الصلاحيات |
| --- | --- |
| مالك الشركة | إدارة الشركة والموظفين والأدوار والفعاليات والبيانات التشغيلية |
| مدير | إدارة الفعاليات والقاعات والضيوف والوفود والمقاعد، ضمن نطاق تفويض المالك |
| منظّم | إدارة الضيوف والوفود والحجوزات دون تغيير العضويات أو ملكية الشركة |
| استقبال | قراءة الحد الأدنى من بيانات الضيوف والمواقع؛ صلاحيات الحضور عند تطويرها، دون إدارة موظفين أو تعديل المخطط |
| قارئ | قراءة التقارير والمعلومات المسموح بها دون تعديل |

يُمنع إزالة آخر مالك نشط للشركة. لا يستطيع مدير ترقية نفسه أو إنشاء مالك جديد إن لم تسمح سياسته. تغيير الدور أو تعطيل العضوية يسري على الطلب التالي ولا ينتظر انتهاء جلسة قديمة.

### Super Admin

- مساحة إدارة منفصلة محمية بهوية مالك المنصة ودور غير قابل للمنح عبر التسجيل العام أو نموذج الشركة.
- تُنشأ هوية مالك المنصة بخطوة bootstrap تشغيلية آمنة، لا بكلمة مرور افتراضية ولا بمعرف محفوظ في JavaScript.
- يدير الشركات وحالاتها والباقات والحدود. تعطيل شركة يوقف الوصول الخادمي إلى عملياتها.
- لا يحصل تلقائيًا على قائمة ضيوف جميع الشركات. أي وصول دعم استثنائي لبيانات شركة يحدد نطاقها وسببه ويُسجل؛ لا توجد وصلة API عامة تتجاوز tenant_id.
- MFA وحماية العمليات الحساسة قبل النشر الإنتاجي؛ تسجيل عمليات التعطيل وتغيير الباقات والصلاحيات.

## 5. دفعات التنفيذ بالترتيب ومعايير القبول

### A. أساس الخادم والمصادقة

- إضافة تطبيق API وتهيئة PostgreSQL وmigrations وتكوين تطوير منفصل عن الموقع المنشور.
- تسجيل مستخدم وشركة وعضوية مالك في معاملة واحدة، وتأكيد البريد والدخول والخروج والاستعادة.
- حماية الجلسات وCSRF والتحقق من Origin وتحديد معدل المحاولات والتعامل مع أخطاء التسجيل دون تسريب حسابات المستخدمين.
- القبول: اختبارات دورة الحساب والجلسة وانتهائها واستعادة كلمة المرور ودعوات أحادية الاستخدام؛ استمرار تشغيل النسخة الحالية دون إعادة تعيين بياناتها.

### B. الشركات والموظفون والعزل

- إنشاء العضويات والأدوار والدعوات، وسياق الشركة وسياسات SQL.
- واجهة مستقلة لكل شركة، وتبديل شركة فقط إذا كان المستخدم عضوًا فيها.
- القبول: اختبار شركتين ومستخدمين بأدوار مختلفة، وإثبات المنع في الخادم وSQL، بما يشمل غياب السياق وتسرب connection pooling.

### C. الفعاليات والقاعات والملكية

- CRUD للشركات المصرح بها على فعاليات وقاعات متعددة، وربط event_hall بمخططه.
- فهرسة الاستعلامات بالملكية والنطاق، وحفظ الضيوف والوفود والحجوزات بعلاقات متسقة.
- القبول: إنشاء فعاليتين وقاعتين لشركة دون تداخل المقاعد، ومنع ربط معرف من شركة أخرى حتى عبر SQL.

### D. ربط وظائف مقعد الحالية بالخادم

- فصل القراءة والحفظ في الواجهة إلى طبقة بيانات تتعامل مع API، مع الحفاظ على تصميم المكونات والوظائف الحالية.
- نقل التحقق من المخطط والوفود والحجز والنقل والتبديل وتقليل الصفوف إلى خدمات خادمية ومعاملات.
- تحديثات متزامنة بتفاؤل مضبوط أو version/ETag؛ رفض التعارض وإعادة تحميل أحدث حالة، دون نجاح وهمي.
- القبول: اختبارات السحب واللمس والتبديل والإخلاء والمرافقين والوفود والتكبير والبحث الحالية على وضع SaaS، واختبار حجزين متزامنين للمقعد نفسه.
- لا يُستخدم localStorage كمصدر بديل للحجوزات عند فشل API أو انتهاء الجلسة؛ تبقى النسخة المحلية القديمة منفصلة بوضوح حتى اكتمال النقل.

### E. استيراد البيانات الحالية دون فقد

- أداة تصدير غير هدّامة تُشغّل من المتصفح الذي توجد فيه البيانات، قبل تعديل مسار الحفظ.
- تصدير النص الأصلي للمفاتيح المهمة مع نسخة مقروءة وإصدار المصدر وبصمة المحتوى؛ تُجرى المعالجة محليًا ولا تُرسل البيانات إلى طرف ثالث لمجرد التصدير.
- شاشة اختيار الشركة المالكة والفعالية والقاعة، مع معاينة dry-run للأعداد والتخصيصات والوفود وأي تعارضات.
- لا يُستنتج مالك البيانات من أسماء المستخدم أو القاعة؛ ولا يُثق بtenant_id داخل الملف. المالك المستهدف يُحدد من الجلسة وصلاحيات الاستيراد.
- الاستيراد معاملة واحدة قابلة للإعادة بأمان، ومفتاح idempotency وبصمة ضمن نطاق الشركة ومصدر الاستيراد؛ لا تُكرر البيانات عند إعادة المحاولة.
- الاحتفاظ بالمعرّفات القديمة في خرائط import_mappings وربط كل ضيف ووفد ومقعد وتخصيص بدقة.
- أي تعارض في بيانات مصدرين يُوقف الاعتماد ويعرض قرار دمج صريحًا؛ لا يُحوّل حجز قائم إلى الانتظار تلقائيًا لإخفاء تعارض الاستيراد.
- القبول: تطابق أعداد الصفوف والكراسي والضيوف والحجوزات والوفود ورؤسائها، ومقارنة التخصيصات واحدًا بواحد، وفشل الاستيراد دون كتابة جزئية عند وجود خطأ.
- تبقى النسخة القديمة وملفات التصدير؛ لا تُمسح مفاتيح المتصفح بعد النجاح. يتاح التراجع إلى النسخة السابقة قبل بدء تشغيل جماعي معتمد.

### F. مالك المنصة والباقات دون دفع

- لوحة Super Admin للشركات والتعطيل والعضويات الإدارية والتدقيق، مع فصل مسارها وصلاحياتها.
- تعريف الباقات واستحقاقاتها وحدود الموظفين والفعاليات والمقاعد، واشتراك داخلي يمكن أن يكون تجريبيًا/مفعّلًا إداريًا.
- لا بوابة دفع ولا خصم أموال أو طلب بطاقات أو تجديد مدفوع في هذه المرحلة.
- القبول: حدود الباقات تُفرض في الخادم، وتعطيل الشركة وإبطال الوصول مسجلان ويعملان دون التأثير على شركة أخرى.

## 6. اختبارات العزل الإلزامية قبل إعلان الجاهزية

| الحالة | النتيجة المطلوبة |
| --- | --- |
| مستخدم A يطلب ضيوف/مقاعد/وفود/تقارير B | رفض دون تسريب محتوى |
| تغيير tenant_id في body أو query أو headers | لا يغير سياق الشركة الموثق ولا يسمح بعملية على B |
| تغيير معرف الفعالية/القاعة/المقعد إلى معرف تابع لـB | رفض API ورفض FK/RLS في PostgreSQL |
| SELECT / INSERT / UPDATE / DELETE بحساب تشغيل التطبيق | نطاق الشركة والصلاحية فقط، حتى دون مرشح برمجي في استعلام الاختبار |
| سياق شركة أو مستخدم مفقود | لا صفوف متاحة ولا كتابة مسموحة |
| إعادة استخدام اتصال A ثم B عبر pool | لا تسرب سياق أو بيانات |
| قارئ يعدّل / منظّم يدير العضويات / استقبال يقرأ حقولًا محظورة | رفض خادمي وصلاحيات قراءة محدودة |
| عضو معطّل أو شركة معلّقة أو جلسة ملغاة | وقف الوصول فورًا |
| تسجيل عام يحاول تعيين Super Admin | رفض |
| حجز متزامن من موظفين للمقعد نفسه | نجاح حجز واحد فقط مع تعارض واضح للآخر |
| تبديل مقعدين | معاملة كاملة أو لا تغيير، دون فقد بيانات أي ضيف |
| استيراد ملف بموارد شركة أخرى أو تكرار الطلب | رفض الربط غير المشروع، وعدم تكرار الاستيراد |
| تسجيل الخروج أو تبديل الشركة في المتصفح | لا تظهر ذاكرة شركة سابقة ولا تُحفظ الحجوزات إلى مخزن محلي مشترك |

هذه اختبارات مخططة، ولم تُنفذ بعد لعدم وجود الخادم وقاعدة البيانات. اختبارات المتصفح الحالية ليست بديلًا عنها.

## 7. حماية النسخة الحالية والنشر التدريجي

- لا reset ولا حذف ولا تعديل تلقائي للبيانات الحالية.
- تطوير النسخة الخادمية على إعداد تجريبي مستقل؛ لا تُفعّل المصادقة أو يُغيّر مصدر الحفظ على الموقع المنشور قبل الاختبارات والاستيراد التجريبي.
- نشر migrations إضافية مع نسخة احتياطية واختبار استعادتها وخطة تراجع؛ لا تُشغّل إسقاطات جداول أو تفريغ بيانات كخطوة إعداد.
- مفتاح تفعيل واضح يميز الوضع المحلي القديم من SaaS؛ لا يخلط بياناتهما ولا يعتبر التخزين المحلي تابعًا للشركة الحالية بمجرد تسجيل الدخول.
- تجربة شركة واحدة على بيانات منسوخة ومصرح بها، ثم التحقق من المطابقة، ثم النقل الفعلي ثم إضافة الشركات الأخرى.
- لا إعلان عن جاهزية أمنية أو نقل ناجح قبل اجتياز اختبارات API وPostgreSQL ومطابقة الحجوزات واختبار بيئة الاستضافة الفعلية.

## 8. المعلومات اللازمة للانتقال من الخطة إلى التنفيذ والنقل

1. هل توجد استضافة API وقاعدة بيانات ومصادقة/بريد يمكن استخدامها، أم تعتمد البنية المقترحة المستقلة؟
2. اسم الشركة المالكة للبيانات الحالية، والمتصفحات/الأجهزة التي تحتوي نسخًا يجب استيرادها. لا تكفي نسخة اختبار المتصفح في بيئة التطوير.
3. وجهة النشر ونطاقها وحساب مالك المنصة قبل التفعيل الإنتاجي. تُدخل بيانات الاتصال والمفاتيح في إعدادات آمنة، لا في المحادثة.

لا يتطلب بدء تصميم المخطط والاختبارات بيانات دخول إنتاجية، لكن تفعيل التسجيل والنشر والإرسال البريدي والنقل الفعلي يعتمد على هذه الإعدادات والملكية.

## قرار الملكية المؤكد

أكد المستخدم أن مالك البيانات الحالية هو «شركة الطريفي». هذا إسناد لخطة الاستيراد، وليس تصريحًا بأن البيانات نُقلت أو أن شركة إنتاجية أُنشئت. لم تُحسم بعد وجهة الاستضافة أو مصادر النسخ الموجودة في متصفحات المستخدمين.

## سجل تنفيذ الأساس المحلي

- أضيفت طبقة `server/` مستقلة: Node/Fastify وPostgreSQL، جلسات خادمية، عضويات وأدوار، فعاليات وقاعات ومخططات، ضيوف وحجوزات ونقل وتبديل، دعوات، إدارة شركات للمالك، وبنية اشتراكات غير مفعلة.
- استُخدمت أدوار قاعدة منفصلة وسياسات RLS قسرية وعلاقات مركبة على بيانات الشركات؛ لا يعتمد العزل على إخفاء الواجهة.
- اجتازت **14 حالة اختبار تكامل على PostgreSQL وAPI**. تشمل منع الوصول بين شركتين، تجاوز الصلاحيات، الحجز المتزامن، النقل والتبديل، وإصداري الاستيراد V2 والقائمة القديمة مع حفظ الأصل.
- اجتاز مسار متصفح حقيقي: التسجيل، إنشاء الموارد و15 كرسيًا، الضيوف، الحجز والتبديل، إعادة التحميل، عرض الجوال، الإخلاء والخروج والدخول.
- اختُبر تكرار تثبيت الاعتماديات والترحيلات وإعادة استخدام قاعدة التطوير دون إعادة تهيئة.
- لم تتغير ملفات الموقع الأصلية، ولم يُرفع هذا الأساس أو يُنشر على GitHub Pages، ولم تُستورد بيانات مستخدم حقيقية. بيانات الاختبارات تخص قاعدة التطوير فقط.
- المتبقي: استكمال نقل جميع وظائف الواجهة وربطها بالخادم، صلاحيات عرض الاستقبال، البريد وتأكيده واستعادة الحساب وMFA، إعداد الاستضافة وTLS والنسخ والاستعادة، ثم نقل بيانات شركة الطريفي المصرح بها ومطابقتها. تشغيل الإنتاج محجوب صراحة حتى استكمال المتطلبات.

## ربط الموقع الحالي بالخادم

نُفذ الربط في `app.js` باستخدام محول `server/public/cloud.js` يقدمه الخادم فقط. تبقى النسخة الثابتة على حفظها المحلي، أما وضع الشركات فيحمّل البيانات ويحفظها من خلال API مصادق عليه وRLS. لا يُستخدم التخزين المحلي بديلًا عند فشل الوصول إلى الشركة.

اختُبرت واجهة الموقع بالحفظ وإعادة التحميل والصفوف وحماية النسخة المحلية ورفض كتابة قديمة، واجتازت مجموعات اختبارات الجذر الأربع. نجحت 16 حالة تكامل SQL/API، تشمل منع الوصول إلى مخطط شركة أخرى وحماية حجوزات قاعة أخرى والحفاظ على هويات الحجوزات. لا يمثل ذلك نشرًا على رابط GitHub Pages؛ لم تُحدد استضافة الخادم بعد ولا تزال متطلبات الإنتاج السابقة قائمة.
